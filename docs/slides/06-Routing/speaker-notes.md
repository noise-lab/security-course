# Lecture 6 — Speaker Notes (Routing Security)

| **Three Pieces of Internet Infrastructure** | Divider. Frame BGP as the *first* shared system attackers can subvert — if you lie to the routing layer, every crypto and login check downstream operates on the wrong endpoint. This week's arc: routing (today) → naming (DNS) next meeting; both were designed for a trusting Internet and had security bolted on later. |
| **What BGP Actually Does** | Keep intuitive — agenda explicitly says NOT to go deep on protocol mechanics. **Autonomous System (AS):** [IANA AS registry](https://www.iana.org/assignments/as-numbers/as-numbers.xhtml). **BGP:** [RFC 4271](https://datatracker.ietf.org/doc/html/rfc4271). Analogy: like asking for directions in chunks — each AS knows only how to reach its own boundary, then hands you off. Cold-call: what's UChicago's AS number? (Answer: [AS 160, U-CHICAGO-AS](https://whois.arin.net/rest/asn/AS160), which originates 128.135.0.0/16; the transit provider in the next slide's example is Cogent, AS 174.) |
| **BGP in One Picture** | The original PowerPoint overview diagram, rendered to a static image (the build animation is gone, so narrate it): clouds are ASes, black lines are BGP sessions between border routers, green arrows are route advertisements, the blue line is traffic flowing the other way toward the destination. The table is a router's view: prefix (128.135.0.0/16 is UChicago's), next-hop, AS path; two rows for one prefix means the router chooses, and everything that follows manipulates that choice. Reference: [RFC 4271 §9, decision process](https://datatracker.ietf.org/doc/html/rfc4271#section-9). |
| **BGP Has Essentially No Security** | The fundamental issue: "transitive trust" — a router will believe any route advertised by a neighbor. Two failure modes to name explicitly: **route leak** (accidental, misconfiguration) vs. **route hijack** (intentional). Both propagate because everyone trusts everyone. Sets up the case-study trio. |
| **Case Study: The 1997 Route Leak** | The "**AS 7007 incident**": MAI Network Services (a small Virginia ISP) misconfigured a router and re-announced the global table with itself as origin; Sprint accepted it. [Wikipedia](https://en.wikipedia.org/wiki/AS_7007_incident) · [Retrospective from Bill Manning on NANOG](https://www.nanog.org/mailinglist/mailarchives/old_archive/1997-04/msg00340.html). Classic "no filtering upstream" — no malice needed. |
| **Case Study: China's "Accidental" Hijack (2010)** | **Apr 8, 2010, China Telecom (AS 23724):** re-originated ~50,000 prefixes for ~18 minutes. Sources: [Renesys, "China's 18-Minute Mystery" (Nov 2010)](https://www.oracle.com/internet-intelligence/) (Renesys now part of Oracle) · [US-China Economic and Security Review Commission report, 2010 (PDF)](https://www.uscc.gov/sites/default/files/annual_reports/2010-Report-to-Congress.pdf) (pp. 243–246). Rosenworcel cited this at the FCC NPRM vote as one of "at least six occasions" of Chinese misrouting. Probably a leak, not a targeted attack, but demonstrates the capability. Discussion: why was it *noticed*? (Performance degraded.) How could the attacker have hidden? (Fewer, more-specific prefixes; shorter window.) |
| **How a Hijack Wins: The AS Path** | BGP's tiebreaker is roughly **shortest AS path** — analogous to picking a road trip by the number of states crossed, not miles. Advertise the same prefix with a shorter path and you win. Reference for BGP path selection: [Cisco's BGP best-path selection algorithm](https://www.cisco.com/c/en/us/support/docs/ip/border-gateway-protocol-bgp/13753-25.html). |
| **Case Study: Pakistan vs. YouTube (2008)** | **Feb 24, 2008:** ordered to block YouTube domestically, Pakistan Telecom (AS 17557) announced a **more-specific /24** of YouTube's /22; leaked upstream via PCCW; **longest-prefix match** meant the /24 won globally. YouTube dark for ~2 hours. [RIPE post-mortem (2008)](https://www.ripe.net/publications/news/industry-developments/youtube-hijacking-a-ripe-ncc-ris-case-study) · [Wikipedia](https://en.wikipedia.org/wiki/Censorship_of_YouTube_in_Pakistan#2008_ban). Two lessons: (1) a domestic censorship action escaped its borders; (2) more-specific always wins regardless of AS path. Bridge to censorship — see the [Censorship breakout](../../breakouts/censorship.md). |
| **What Attackers Can Do With a Hijack — Vignette** | **July 9–12, 2025 APNIC/LACNIC hijack:** three short attacks that combined a technical attack with social engineering. **Primary sources:** [APNIC Blog, "RPKI vs social engineering: A case study in route hijacking" (Mar 31, 2026)](https://blog.apnic.net/2026/03/31/rpki-vs-social-engineering-a-case-study-in-route-hijacking/) · [LACNIC Blog version](https://blog.lacnic.net/en/rpki-vs-social-engineering-a-case-study-in-route-hijacking/) · [APRICOT 2026 / APNIC 61 SIG session recap](https://blog.apnic.net/2026/03/12/apnic-routing-security-sig-at-apricot-2026-social-engineering-rpki-aspa-ta-constraints/). Presented by Carlos Martínez-Cagnazzo (LACNIC CTO) and Sanjaya (APNIC). Attacker used forged corporate identity documents and a lookalike domain to convince a multinational upstream provider to enable a BGP session for an unauthorized ASN; injected short announcements of LACNIC address space. First detection: a user's email silently vanished. Resolved by coordinated confirmation from APNIC, LACNIC, APJII/IDNIC and the real ASN holder. Teaching moment: crypto is only as strong as the human process around it — see also [ASPA (RFC 9774)](https://datatracker.ietf.org/doc/rfc9774/) which would have caught the forged upstream relationship. |
| **Redirection, Drawn: Two Routes to Lie About** | Recovered diagram from the original deck (pptx slide 16); the clouds built one at a time, so walk it.<br>• **What the picture says:** the user's packets ride two separate BGP routes before a login page loads, one to the authoritative DNS server and one to the web server; either route can be hijacked.<br>• **DNS route:** whoever receives the queries bound for the authoritative server answers them, so the name maps wherever the attacker likes, with no resolver cache poisoned in the classic sense.<br>• **Web route:** the blunt version; the attacker simply is the bank for the duration of the hijack.<br>• **"SSL should protect, but…":** the same hijack can intercept the CA's domain-validation traffic (HTTP-01 / DNS-01 in ACME), so the attacker obtains a legitimate certificate; this is why CAs now validate from multiple vantage points. Reference: [RFC 8555 (ACME)](https://datatracker.ietf.org/doc/html/rfc8555) for the validation methods.<br>• **Course tie-in:** sets up the DNS lecture (same route, different target) and the "Two Problems" slide that follows. |
| **Interception, Step by Step** | Two frames from a three-slide build in the original deck (pptx slides 22 and 24; 23 was the planning step). Figures after Pilosov and Kapela, DEFCON 16.<br>• **Read first:** [Pilosov and Kapela, "Stealing the Internet" (DEFCON 16, 2008, PDF)](https://www.defcon.org/images/defcon-16/dc16-presentations/defcon-16-pilosov-kapela.pdf), the talk these figures come from and the first public live BGP MITM demo.<br>• **Before:** the target (AS 200) originates 10.10.220.0/22; after convergence every AS's forwarding path (dotted blue) ends at the target.<br>• **Planning (the missing middle frame):** the attacker traceroutes to the target and records the ASes on its own path there, AS 10 and AS 20.<br>• **The trick:** AS 100 announces a more-specific /24, which wins everywhere by longest-prefix match, but prepends 10, 20 and 200 to the AS path; BGP loop detection makes those ASes drop an announcement containing their own number, so they keep the honest route.<br>• **After:** the rest of the Internet forwards the /24 to AS 100; a static route there pushes it to AS 10, which still routes honestly to the target. The original deck's slides 25–28 showed TTL rewriting to hide the extra hops from traceroute.<br>• **What stops it today:** a ROA with a tight maxLength makes the /24 RPKI-invalid; a broad maxLength does not, which is exactly the gap in the July 2025 APNIC/LACNIC case on the previous slide. ASPA ([RFC 9774](https://datatracker.ietf.org/doc/rfc9774/)) would also catch the forged provider relationship.<br>• **Ask:** how would the target ever notice? Only by latency or by a traceroute that shows unexpected ASes, and the attacker rewrites TTLs to hide those. |
| **Two Problems We Must Solve** | Divider. The two-part question a receiver must answer: origin auth (was this AS allowed to originate?) and path auth (is the AS path real?). Map back to the case studies: 2010 China Telecom = bogus origin; a path-shortening attack = falsified path. Foreshadow: only one is deployed, and the reason is incentives, not crypto. |
| **Origin Authentication With RPKI** | **RPKI:** [RFC 6480 (architecture)](https://datatracker.ietf.org/doc/html/rfc6480), [RFC 6482 (ROA format)](https://datatracker.ietf.org/doc/html/rfc6482). Registries as roots of trust: [ARIN](https://www.arin.net/resources/manage/rpki/), [RIPE NCC](https://www.ripe.net/manage-ips-and-asns/resource-management/rpki/), [APNIC](https://www.apnic.net/community/security/resource-certification/), [LACNIC](https://www.lacnic.net/rpki), [AFRINIC](https://www.afrinic.net/services/rpki). Reuse the PKI mental model: CA → registry, cert → ROA, identity → address ownership. **Route Origin Validation (ROV):** [RFC 6483](https://datatracker.ietf.org/doc/html/rfc6483) — states Valid, Invalid, NotFound. |
| **The Address Hierarchy Is Already a Tree** | Recovered figure (pptx slide 40); it is the address-allocation hierarchy from Kent, Lynn and Seo, "Secure Border Gateway Protocol (S-BGP)," IEEE JSAC 18(4), 2000, so credit it when showing. Names are dated (GTE-I, MCI); the shape is today's RPKI.<br>• **Walk it top-down:** IANA/ICANN holds all address space, delegates blocks to the five regional registries, which delegate to ISPs, which delegate to customers.<br>• **The point:** each arrow is a delegation that already happened administratively, so turning it into a certificate chain adds no new trust relationship; that is why origin authentication could be built and deployed while path authentication stalled.<br>• **Contrast with the web PKI** from the earlier lecture: a CA must go and verify that you control a domain; a registry already knows who holds a block because it issued it.<br>• **Trust anchors:** each RIR publishes its own; a validator holds those five the way a browser holds root CAs. Architecture: [RFC 6480](https://datatracker.ietf.org/doc/html/rfc6480).<br>• **Ask:** what happens when a block is transferred between registries, or when AFRINIC's governance crisis stalls its trust anchor? Good hook for the incentives discussion two slides on. |
| **Why Origin Authentication Got Deployed** | The incentive story: self-protecting + locally deployable. **Current numbers (mid-2026):** [NIST RPKI Monitor](https://rpki-monitor.antd.nist.gov/) shows ~60% of IPv4 routes covered by ROAs, up from the 50% milestone in [May 2024](https://www.kentik.com/blog/rpki-rov-deployment-reaches-major-milestone/). **~70% of internet traffic** heads to ROA-covered prefixes ([Kentik](https://www.kentik.com/blog/rpki-rov-deployment-reaches-major-milestone/)). But **only ~12.3% of ASes are "fully protected"** by ROV filtering ([RoVista / NANOG 90](https://nanog.org/stories/articles/rpki-rov-deployment-reaches-major-milestone/)) — coverage is not enforcement. Live view: [Cloudflare Radar RPKI dashboard](https://radar.cloudflare.com/routing/rpki) (expanded April 2026). Recent Tier-1 flips to enforce: [Bell Canada Aug 2025, Sparkle Feb 2026](https://isbgpsafeyet.com/). |
| **But RPKI Only Checks the Origin** | Key midterm insight: a Valid ROA does not mean a valid path. The path-shortening attack keeps the true origin (RPKI happy) but *deletes* an intermediate AS to appear more attractive. Have students reason about it as an induction step: what if AS100 lies about who its neighbor is? |
| **Path Shortening, Drawn** | Recovered diagram (pptx slide 42), the picture version of the AS100/AS6167/AS22394 example on the previous slide. The "AS Path = 2 4" label wraps onto two lines in the render; read it as one path.<br>• **Walk the red arrows:** AS 4 originates; its announcement reaches AS 1 via 4 → 3 → 2 → 1 (three hops) and via 4 → 6 → 1 (two hops), so AS 1 prefers AS 6.<br>• **The lie:** AS 2 (shaded) deletes AS 3 and advertises "2 4"; now it ties the honest route on length and wins with any local preference or tie-break in its favour, pulling AS 1's traffic through itself.<br>• **Why RPKI is silent:** the origin field still says AS 4, so ROV returns Valid; nothing in plain BGP lets AS 1 check whether AS 2 and AS 4 are neighbours.<br>• **Ask before advancing:** what would AS 1 need to see to catch this? Answer on the next slides: proof that AS 4 actually handed the route to AS 2. |
| **Path Authentication: Sign the Path** | **BGPsec:** [RFC 8205](https://datatracker.ietf.org/doc/html/rfc8205). Historical precursor: **S-BGP** (Kent, Lynn, Seo, IEEE JSAC 2000). Critical detail flagged for midterm: each signature must cover both **the path so far** *and* **the recipient AS**. That's what stops shortening and false-edge attacks. Same trick as certificate chains — reuse the mental model. |
| **What the Signature Must Cover** | Two recovered diagrams (pptx slides 43 and 54; the second was a hidden slide from the soBGP comparison this deck skips). They make the "sign the path so far and the recipient" rule concrete.<br>• **Top, shortening:** to announce "2 4", AS 2 must present a chain whose first link is AS 4 signing "path 4, sent to AS 2"; AS 4 only ever signed "sent to AS 3", so the chain cannot be built.<br>• **Bottom, false edge:** AS 3 is adjacent to AS 1 but not AS 4; it invents the edge 3–4 and offers path 1 3 4; the missing piece is AS 4's signed attestation naming AS 3 as recipient.<br>• **The invariant:** every signature covers the path so far plus the next AS, so neither removing a hop nor inventing one verifies. This is the midterm-style question: what must be signed, and why signing only prefix and origin is not enough.<br>• **Caveat that sets up the next slide:** if AS 3 and AS 4 collude, they can sign an edge that exists on paper but not on the wire, and BGPsec cannot tell. Spec: [RFC 8205 (BGPsec)](https://datatracker.ietf.org/doc/html/rfc8205). |
| **What Path Authentication Still Can't Do** | Honest gap: securing the *control* plane is not securing the *data* plane. Even fully signed paths leave: no data-plane guarantee, suppression, replay, collusion. Recent framing: [Cloudflare's BGP first-AS enforcement note](https://blog.cloudflare.com/rpki-updates-data/). "BGPsec is deployed" would still not mean "routing is safe." |
| **Control Plane vs. Data Plane, Drawn** | Recovered diagram (pptx slide 18); it built in two clicks, announcement first, then deflection, so narrate in that order.<br>• **Red:** AS 1 announces "AS Path = 1 2 …" to its left-hand neighbour; with BGPsec every AS on that path has signed its link and the announcement verifies.<br>• **Blue:** the packets enter AS 1, reach a router whose internal routing (iBGP, IGP, a static route, a bad route-map) points at the wrong exit, and leave toward AS 3; a deflection, not a hijack, since no false announcement was ever made.<br>• **The point:** control-plane security is a statement about messages; the forwarding table is built from messages plus local policy plus mistakes, and signatures say nothing about the latter two.<br>• **Current anchor:** the October 4, 2021 Facebook outage, where the withdrawals were correct and the data plane simply had nowhere to go; [Cloudflare's write-up](https://blog.cloudflare.com/october-2021-facebook-outage/) is the clearest account.<br>• **If asked about fixes:** traceroute-based detection, path-aware networking research, and RPKI-to-router (RTR), which still only feeds the control plane. |
| **So Why Isn't Path Authentication Deployed?** | Name it: coordination problem / tragedy of the commons. Assigned reading: **"Why is it taking so long to secure Internet routing?" — Sharon Goldberg, *CACM* Oct 2014**, still the canonical explainer ([CACM article](https://cacm.acm.org/magazines/2014/10/178771-why-is-it-taking-so-long-to-secure-internet-routing/fulltext)). Debate seed: should path auth be *regulated* into existence, or does that just create paper compliance? |
| **A Policy Lever: The FCC Steps In** | **FCC NPRM (June 6, 2024, PS Docket 24-146):** [Federal Register notice](https://www.federalregister.gov/documents/2024/06/17/2024-13048/reporting-on-border-gateway-protocol-risk-mitigation-progress-secure-internet-routing) · [FCC Fact Sheet (DOC-402609A1)](https://docs.fcc.gov/public/attachments/DOC-402609A1.pdf) · [Full NPRM (FCC 24-62)](https://docs.fcc.gov/public/attachments/FCC-24-62A1.pdf). Nine largest BIAS providers file confidential annual plans plus quarterly reports; excused if ROAs cover ≥90% of originated routes. **Status as of mid-2026:** comments closed Aug 1, 2024; **no final rule adopted**; proceeding still open. The 2025 FCC leadership change and legal challenges to Title II reclassification (which supplies the authority) make the future uncertain. Rosenworcel's floor statement cited China Telecom "on at least six occasions." The [Routing breakouts](../../breakouts/routing.md) argue both sides of this mandate. |
| **Bonus Defenses You'll See in the Wild** | **TCP-MD5:** [RFC 2385](https://datatracker.ietf.org/doc/html/rfc2385). **TCP-AO:** [RFC 5925](https://datatracker.ietf.org/doc/html/rfc5925) (replacement). **GTSM (Generalized TTL Security Mechanism):** [RFC 5082](https://datatracker.ietf.org/doc/html/rfc5082) — most eBGP peers are one hop away; send TTL=255, reject arriving TTL<254; a remote attacker can't forge a high enough TTL. Clever, cheap, deployable. Protects the *session*, not *what* is announced — necessary, not sufficient. The GTSM diagram on the slide is recovered from the original deck (pptx slide 31): two border routers, one sending TTL 255, the other rejecting anything below 254. |
