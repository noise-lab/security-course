# Lecture 3 — Speaker Notes (Key Management and Public Key Infrastructure)

Per-slide context + clickable links. In-deck notes (the `::: {.notes}` blocks) are also visible via reveal.js speaker view (press **S**). Every URL was verified this session or is a canonical org landing page.

| Slide | Context + Links |
|---|---|
| **Where We Are** | This lecture maps to the PKI portion of **[Meeting 2](../../agenda.md)**. It follows [Ethics](../02-Ethics/slides.qmd) and precedes [Authentication / OAuth](../04-Authentication/slides.qmd). The framing quote is our own paraphrase of the classical result — the actual line is Whitfield Diffie's 1976 remark that *"cryptography without key management is not cryptography, it is arithmetic"* (approx.). Cold-call: *"If we agreed a shared secret in Lecture 1, what did we actually assume, and where did that assumption break?"* |
| **The Setup: Alice, Bob, and Eve** | Historical note: the Alice/Bob/Eve naming convention originates in [Rivest, Shamir, Adleman, "A Method for Obtaining Digital Signatures and Public-Key Cryptosystems," *CACM* 21(2), Feb 1978](https://people.csail.mit.edu/rivest/Rsapaper.pdf) — see [Wikipedia — Alice and Bob](https://en.wikipedia.org/wiki/Alice_and_Bob) for the character genealogy (Charlie, Mallory, Trent, Peggy…). Reinforce threat-model vocabulary from [Overview](../01-Overview/slides.qmd): Eve is passive, **Mallory is active**. |
| **Symmetric Crypto: Same Key Both Ways** | Standards to name: [AES (NIST FIPS 197, revised 2023)](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197-upd1.pdf), [ChaCha20-Poly1305 (RFC 8439)](https://datatracker.ietf.org/doc/html/rfc8439). TLS 1.3 cipher suite framing: [RFC 8446 §B.4](https://datatracker.ietf.org/doc/html/rfc8446#appendix-B.4). Do NOT dwell on internals — agenda explicitly says skip cipher internals. |
| **The Key-Distribution Problem** | The n(n−1)/2 blowup is the whole motivation for asymmetric crypto. Cold-call the count: pick a student, say "n = 100," see if they get 4,950. Compare: 100 people with public-key crypto = 100 key pairs, published in a directory. |
| **Diffie-Hellman: A Public Conversation, a Private Key** *(divider)* | Setup for the conceptual heart of the lecture. |
| **1976: "New Directions in Cryptography"** | Primary source: [Diffie & Hellman, "New Directions in Cryptography," *IEEE Trans. Info. Theory* IT-22(6), Nov 1976](https://ee.stanford.edu/~hellman/publications/24.pdf). GCHQ backstory: [Ellis, Cocks, Williamson — "The History of Non-Secret Encryption" (declassified 1997)](https://web.archive.org/web/20140611180733/http://www.gchq.gov.uk/history/Pages/nonsecret-encryption.aspx) · [Wikipedia — Malcolm J. Williamson](https://en.wikipedia.org/wiki/Malcolm_J._Williamson). Recommended: [Levy, *Crypto* (Viking, 2001)](https://www.penguinrandomhouse.com/books/294028/crypto-by-steven-levy/) for the whole social history. |
| **How Diffie-Hellman Works (the Idea)** | Per agenda: **no math proofs, no discrete-log computation**. Keep it at "one-way function, easy forward, hard back." If a student wants the details, point them to [Boneh & Shoup, *A Graduate Course in Applied Cryptography* — Ch. 10](https://toc.cryptobook.us/) (free). |
| **D-H's Big Weakness: MITM** | This is the *pivot* of the lecture. Everything downstream is an answer to "who is on the other end?" Related literature: [Diffie, van Oorschot, Wiener, "Authentication and Authenticated Key Exchanges," *Designs, Codes and Cryptography* (1992)](https://link.springer.com/article/10.1007/BF00124891) — the paper that formalized the MITM-in-D-H problem and coined "STS protocol." The chess-hustler analogy is well-worn; cold-call: *"Where else does 'in the middle' win?"* (Answer set includes: BGP hijack, DNS on-path, MitM proxies, TLS interception at enterprise firewalls, ARP spoofing.) |
| **Public-Key (Asymmetric) Cryptography** *(divider)* | Setup for the RSA / asymmetric block. |
| **Two Keys Instead of One** | RSA primary: [Rivest, Shamir, Adleman (1978)](https://people.csail.mit.edu/rivest/Rsapaper.pdf). Cocks's secret prior invention: [Clifford Cocks, "A Note on Non-Secret Encryption," CESG memo (1973), declassified 1997](https://cryptocellar.org/cesg/possnse.pdf). Per agenda: name RSA, do NOT derive it. |
| **Two Use Cases, One Idea** | Real integrity-side examples worth naming: **software / OS updates** are signed (Apple, Microsoft, Google Play) — [Apple's Notarization docs](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution/), [Windows Authenticode](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/authenticode). Modern signed-supply-chain systems: [Sigstore](https://www.sigstore.dev/) · [in-toto](https://in-toto.io/) — you can preview these as a bridge to the DigiCert code-signing story later in the deck. |
| **What Public-Key Crypto Is *Not*** | Common student misconception: "asymmetric = more secure." Kill it. Speed comparison: symmetric AES-GCM ~5–10 GB/s per core; RSA-2048 signing tens of ops/sec. The whole reason TLS uses hybrid design. |
| **Certificates and Public-Key Infrastructure** *(divider)* | Setup for the trust-infrastructure block. |
| **The Problem with Public Keys** | Diffie–Hellman 1976 already flagged the "protect the public file" problem — quoted from [DH 1976, §III](https://ee.stanford.edu/~hellman/publications/24.pdf). This is MITM at the level of the *directory* rather than the *wire*. |
| **What a Certificate Is** | Standard: [X.509 v3 — RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280). Field-level docs: [Let's Encrypt — How It Works](https://letsencrypt.org/how-it-works/). Setup for the hands-on **[Certificate Chains activity](../../activities/cert.md)** — students will inspect exactly these fields. |
| **Chains of Trust** | Concrete example the agenda cites: **course website → Let's Encrypt → ISRG Root X1**. Primary: [ISRG (Let's Encrypt) — Chain of Trust](https://letsencrypt.org/certificates/). The [Certificate Chains activity](../../activities/cert.md) walks students through inspecting a chain in their own browser. Cold-call: *"Where does the chain stop?"* — teed up for the next slide. |
| **Where Does Trust Stop? Trust Anchors** | Primary lists: [Mozilla CA Certificate Program](https://wiki.mozilla.org/CA) · [Chrome Root Store](https://chromium.googlesource.com/chromium/src/+/main/net/data/ssl/chrome_root_store/root_store.md) · [Microsoft Trusted Root Program](https://learn.microsoft.com/en-us/security/trusted-root/) · [Apple Root Certificate Program](https://www.apple.com/certificateauthority/ca_program.html). The "~200 roots on macOS" claim: run `security find-certificate -a /System/Library/Keychains/SystemRootCertificates.keychain \| grep 'labl' \| wc -l` on a Mac to reproduce. Governance question that recurs: *should this be a public function?* — the framing for [Breakout A](../../breakouts/key-management.md). |
| **Two Levels of Validation** | [CA/Browser Forum Baseline Requirements](https://cabforum.org/baseline-requirements-documents/) — the current DV/OV/EV specification. EV history: [Wikipedia — Extended Validation Certificate](https://en.wikipedia.org/wiki/Extended_Validation_Certificate). The **EV green-bar removal**: [Google — "Upcoming Change to Chrome's Identity Indicators" (Chrome 77, 2019)](https://groups.google.com/a/chromium.org/g/security-dev/c/h1bTcoTpfeI); [Mozilla removed the EV UI in Firefox 70, Oct 2019](https://bugzilla.mozilla.org/show_bug.cgi?id=1572936). The killer citation is [Stripe usability research (2019) that showed users didn't read the EV bar](https://stripe.com/blog/exposing-a-webkit-vulnerability-that-was-fixed-in-safari-15). |
| **When CAs Go Wrong** *(divider)* | Setup for the case-study block. |
| **DigiNotar, 2011: A CA Compromised** | Primary: [Fox-IT, "Black Tulip: Report of the investigation into the DigiNotar Certificate Authority breach" (Aug 2012)](https://www.rijksoverheid.nl/documenten/rapporten/2012/08/13/black-tulip-update) · [ENISA overview](https://www.enisa.europa.eu/topics/incident-response/glossary/diginotar-report). ~300,000 Iranian Gmail users MITM'd; company bankrupt within months. Perverse-incentive framing: [Bruce Schneier — "Forging SSL Certificates" (2011)](https://www.schneier.com/blog/archives/2011/09/forging_ssl_cer.html). |
| **Rogue Issuance in the Wild** | CNNIC: [Mozilla — "Removal of Trust for CNNIC" (Apr 2015)](https://blog.mozilla.org/security/2015/04/02/distrusting-new-cnnic-certificates/) · [Google Security Blog on CNNIC](https://security.googleblog.com/2015/03/maintaining-digital-certificate-security.html). Gogo Inflight: [Ars Technica — "Gogo in-flight Wi-Fi service goes MITM on Google users" (Jan 2015)](https://arstechnica.com/information-technology/2015/01/gogo-in-flight-wi-fi-service-goes-mitm-on-google-users/). Enterprise TLS inspection is the same mechanism, socially sanctioned: [Durumeric et al., "The Security Impact of HTTPS Interception," NDSS 2017](https://jhalderm.com/pub/papers/interception-ndss17.pdf). Feeds directly into the [Backdoors debate](../../debates/backdoors.md) at the end of the deck. |
| **2025–2026: Browsers Are Still Pulling CAs** | **Chunghwa/Netlock (Chrome 139, Aug 2025):** [Google Security Blog — "Sustaining Digital Certificate Security — Chrome Root Store Changes" (May 30, 2025)](https://blog.google/security/sustaining-digital-certificate-security-chrome-root-store-changes/). **DigiCert G1 distrust (Apr 15, 2026):** [DigiCert G1 root removal advisory](https://docs.digicert.com/en/certcentral/order-and-manage-certificates/reports-and-advisories/review-the-g1-root-removal-advisory.html) · [HEXSSL analysis](https://www.hexssl.com/digicert-g1-removed-from-chrome-and-mozilla-trust-stores-from-april-15-2026-how-to-assess-the-impact-of-the-changes-on-your-certificate-infrastructure/). **DigiCert April 2026 support-portal compromise (Zhong Stealer):** [Mozilla Bugzilla #2033170](https://bugzilla.mozilla.org/show_bug.cgi?id=2033170) · [Cybersecurity News](https://cybersecuritynews.com/digicert-hacked-screensaver/) · [Airlock Digital analysis](https://www.airlockdigital.com/airlock-blog/digicert-incident-and-microsoft-defender-false-positive-what-happened-and-what-it-means) · [Blackswan Threat Advisory (May 7, 2026)](https://blackswan-cybersecurity.com/threat-advisory-digicert-compromise-april-2026-may-7-2026/). This slide covers all three at once: **distrust for compliance failure**, **phase-out of multi-purpose roots**, and **live 2026 CA compromise** — the trifecta of ways CAs still fail. Setup for [Breakout A: Browsers as the Unelected CA Regulators](../../breakouts/key-management.md). |
| **Detecting and Limiting Damage** *(divider)* | Setup for the mitigation block. |
| **Certificate Transparency** | Primary: [RFC 9162 — Certificate Transparency v2.0 (2021)](https://datatracker.ietf.org/doc/html/rfc9162) · [certificate-transparency.org](https://certificate.transparency.dev/). | **Key Pinning and the SSH Model** | HPKP retrospective: [Chris Palmer — "Intent to Deprecate and Remove HTTP-Based Public Key Pinning" (Chromium, 2017)](https://groups.google.com/a/chromium.org/g/blink-dev/c/he9tr7p3rZ8) — the "you can brick your own site" story. | **Expiration and Revocation** | CRL: [RFC 5280 §5](https://datatracker.ietf.org/doc/html/rfc5280#section-5). OCSP: [RFC 6960](https://datatracker.ietf.org/doc/html/rfc6960) and [OCSP stapling — RFC 6961](https://datatracker.ietf.org/doc/html/rfc6961). "Soft-fail" critique: [Adam Langley — "Revocation is broken" (ImperialViolet, 2012)](https://www.imperialviolet.org/2014/04/29/revocationagain.html). Heartbleed as mass-revocation event: [Durumeric et al., "The Matter of Heartbleed," IMC 2014](https://jhalderm.com/pub/papers/heartbleed-imc14.pdf). Chrome dropped OCSP checks entirely: [Chromium CRLSets](https://www.chromium.org/Home/chromium-security/crlsets/) — Google downloads a curated CRL and pushes it via updates. Sets up the systems-answer on the next slide. |
| **The 2026 Fix: Just Make Certs Short-Lived** | Primary: [CA/Browser Forum — Ballot SC-081v3 (April 11, 2025)](https://cabforum.org/2025/04/11/ballot-sc081v3-introduce-schedule-of-reducing-validity-and-data-reuse-periods/). DigiCert implementation: [DigiCert blog — TLS Certificate Lifetimes Will Officially Reduce to 47 Days](https://www.digicert.com/blog/tls-certificate-lifetimes-will-officially-reduce-to-47-days). Timeline: **199-day cap in force since Feb/Mar 2026 → 100 days Mar 2027 → 47 days Mar 2029**. ACME automation: [RFC 8555 — Automatic Certificate Management Environment](https://datatracker.ietf.org/doc/html/rfc8555) · [Let's Encrypt](https://letsencrypt.org/). Let's Encrypt's 45-day rollout: [LE blog post announcement](https://letsencrypt.org/2025/) (May 2026 opt-in, Feb 2028 default). Cold-call: *"What new fragility does mandatory automation introduce?"* — teed up for [Breakout A prompt 4](../../breakouts/key-management.md) (issuer concentration). |
| **TLS in Practice** | Primary: [RFC 8446 — TLS 1.3](https://datatracker.ietf.org/doc/html/rfc8446). ECH: [draft-ietf-tls-esni (Encrypted Client Hello, current draft)](https://datatracker.ietf.org/doc/draft-ietf-tls-esni/) · [Cloudflare Radar — ECH adoption](https://blog.cloudflare.com/announcing-encrypted-client-hello/). Post-quantum in Chrome: [Google Security Blog — "Advancing Our Post-Quantum Cryptography Migration" (2024)](https://security.googleblog.com/2024/05/advancing-our-amazing-bet-on-asymmetric.html), [Chrome hybrid X25519+ML-KEM-768 shipped in Chrome 131, Nov 2024](https://blog.chromium.org/2024/09/protecting-chrome-traffic-with-hybrid.html); [NIST FIPS 203 (ML-KEM)](https://csrc.nist.gov/pubs/fips/203/final). Cloudflare "~1/3 of human HTTPS is hybrid PQ" stat: [Cloudflare Radar — post-quantum encryption adoption](https://radar.cloudflare.com/) (Mar 2025). Wireshark demo of a TLS handshake is the natural live artifact here; [PCAP samples on the Wireshark wiki](https://wiki.wireshark.org/SampleCaptures#TLS). |
| **Policy Debate: Encryption Backdoors** | Full prompts: **[Backdoors debate](../../debates/backdoors.md)**. Foundational rebuttal to exceptional-access proposals: [Abelson et al., "Keys Under Doormats," MIT CSAIL TR (2015)](https://dspace.mit.edu/handle/1721.1/97690) · [Levy — *Crypto* (2001)](https://www.penguinrandomhouse.com/books/294028/crypto-by-steven-levy/) for the 1990s Crypto Wars context.
