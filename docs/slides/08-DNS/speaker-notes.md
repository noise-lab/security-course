| **When DNS Breaks, the Internet Breaks** | **AWS us-east-1 DynamoDB DNS outage, October 20, 2025.** Primary source: AWS's own post-event summary (linked from the [AWS Health Dashboard](https://health.aws.amazon.com/health/status)). Independent analyses verified 2026-07-16: [InfoQ — Race Condition in DynamoDB DNS System (Nov 2025)](https://www.infoq.com/news/2025/11/aws-dynamodb-outage-postmortem/) · [ThousandEyes — AWS Outage Analysis: October 20, 2025](https://www.thousandeyes.com/blog/aws-outage-analysis-october-20-2025) · [The Register — "A single DNS race condition brought AWS to its knees"](https://www.theregister.com/2025/10/23/amazon_outage_postmortem/) · [The Pragmatic Engineer — What caused the large AWS outage?](https://blog.pragmaticengineer.com/aws-outage-us-east-1/). The mechanism: a stale-plan check in the `DNS Enactor` allowed an old plan to overwrite a newer one, and cleanup automation then deleted the plan entirely — leaving `dynamodb.us-east-1.amazonaws.com` with an empty DNS record. Cascade: DynamoDB → DropletWorkflow Manager → EC2 lease-timeouts → "congestive collapse." ~15 hours; Snapchat, Fortnite, Roblox, Ring, McDonald's mobile, HMRC. **Not an attack — just DNS.** The teaching point: DNS is a single dependency small enough for the whole cloud to trip over. Hold this centralization thread; we return to it under "Architectural Crisis." |
| **What DNS Does** | [MDN — What is DNS?](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/DNS) · [Cloudflare Learning — What is DNS?](https://www.cloudflare.com/learning/dns/what-is-dns/). Emphasize the design goals — scalability, decentralized control, global consistency. These are exactly what encrypted-DNS centralization later strains. |
| **The DNS Hierarchy** | The recursive resolver is the workhorse and the privacy chokepoint (it sees who you are AND what you ask). Reference for the walk-through: [ICANN Beginner's Guide to DNS](https://www.icann.org/en/system/files/files/domain-names-beginners-guide-06dec10-en.pdf). |
| **A Single Lookup, Step by Step** | Likely midterm question. "Hundreds of lookups per page" sets up website fingerprinting — each page has a distinctive set of names. |
| **The Problem: DNS Had No Authentication** | **The Kaminsky attack (2008).** Primary anchor: [CERT Vulnerability Note VU#800113 — Multiple DNS implementations vulnerable to cache poisoning (July 8, 2008)](https://www.kb.cert.org/vuls/id/800113). Overview: [Dan Kaminsky — Wikipedia](https://en.wikipedia.org/wiki/Dan_Kaminsky). The fix (mostly): source-port randomization on top of TXID randomization — reduces the guess space from 2^16 to ~2^32. Not the end of the story: [SAD DNS (2020)](https://www.saddns.net/) showed cache poisoning could return via ICMP side channels. Reference: [Illustrated Guide to the Kaminsky DNS Vulnerability](http://unixwiz.net/techtips/iguide-kaminsky-dns-vuln.html). Agenda flags mechanics as conceptual only — keep the exam framing at "why did the lie propagate to everyone." |
| **DNSSEC: Signatures Up the Hierarchy** | Reference: [IETF RFC 4033-4035](https://datatracker.ietf.org/doc/html/rfc4033) · [ICANN — DNSSEC What Is It and Why Is It Important?](https://www.icann.org/resources/pages/dnssec-what-is-it-why-important-2019-03-05-en). Validation stats (verified 2026-07-16): still <40% globally by end-user resolver share ([APNIC's DNSSEC validation dashboards](https://stats.labs.apnic.net/dnssec)). Use DNSSEC as a test of whether students understand PKI: who signs what, where the chain bottoms out. Connect to web PKI and RPKI from earlier lectures. |
| **Where Does the Chain of Trust Stop?** | Callback to Lecture 1 (Thompson's "Reflections on Trusting Trust"). Every trust hierarchy bottoms out in a root you can't independently verify. This recurs throughout the course. |
| **DNS Leaks More Than You Think** | The "just metadata" line is the hook — metadata *is* content here: the names you resolve are the sites you read. Ask: do you trust your ISP/university with the full log of everything you look up? |
| **Your Devices Announce Themselves** | This table from the IoT-inspection work is the most memorable artifact in the deck. Even encrypted *content* leaves these names exposed if DNS is unencrypted. Ties to the smart-home / surveillance themes later in the course. Companion reference: the "IoT Inspector" line of work at Princeton — [iotinspector.org](https://iotinspector.org/). |
| **Website Fingerprinting** | Even Tor exit DNS leaks the site — [Greschbach, Pulls, Roberts, Winter, Feamster — *"The Effect of DNS on Tor's Anonymity,"* NDSS 2017](https://www.ndss-symposium.org/wp-content/uploads/2017/09/ndss2017_04A-1_Greschbach_paper.pdf). The unique-name statistic drives why fingerprinting works so well. |
| **Existing Approaches** | [RFC 7858 — DNS over TLS (DoT)](https://datatracker.ietf.org/doc/html/rfc7858) · [RFC 8484 — DNS over HTTPS (DoH)](https://datatracker.ietf.org/doc/html/rfc8484) · [RFC 9250 — DNS over QUIC (DoQ)](https://datatracker.ietf.org/doc/html/rfc9250) · [RFC 9156 — QNAME Minimization](https://datatracker.ietf.org/doc/html/rfc9156). DNSSEC is in a different column: integrity, not secrecy. |
| **The First Hop Is the Adversary** | Set up the DoH pitch: the eavesdropper you most worry about is often the first hop, the network you're sitting on. Encrypting to that resolver doesn't help if that resolver is the adversary. |
| **DNS-over-HTTPS (DoH)** | Mozilla's rollout: [Firefox — Understand DNS-over-HTTPS](https://support.mozilla.org/en-US/kb/dns-over-https-doh-faqs). Chrome's rollout: [Google Security Blog on Secure DNS (Chrome 83, May 2020)](https://security.googleblog.com/2020/05/a-safer-and-more-private-browsing-DoH.html). Cloudflare / Google Public DNS references: [Cloudflare 1.1.1.1](https://one.one.one.one/) · [Google Public DNS](https://developers.google.com/speed/public-dns). |
| **DoH Changes *Who* You Trust — Not *Whether*** | The slide they should remember. DoH genuinely fixes path eavesdropping, but the third-party resolver now holds the complete log. "You changed who you trust, not whether you trust someone." |
| **On by Default — Do Users Know?** | User-study grounding: our own work on encrypted-DNS defaults and understanding. Firefox and Android UI screenshots on the slide are the artifacts most students recognize. Default = de facto policy. |
| **Users Don't Understand — or Trust — Resolvers** | Pilot survey findings; write-up is our lab's work. The interface and information matter. Where security/privacy engineering meets consumer-protection policy. |
| **DoH Can Even Perform Well** | Kills the "encryption is too slow" objection with data. So the real debate is governance, not latency. Foreshadows ODoH: Cloudflare's original objection ("too much latency") was empirically wrong. |
| **The Architectural Crisis: Centralization** | Bring the opening AWS vignette full circle and add the 2026 coercion vector. Verified 2026-07-16: **(a) Italy AGCOM €14.2M fine on Cloudflare** for refusing to filter pirate domains on public 1.1.1.1 — [TorrentFreak coverage (Jan 2026)](https://torrentfreak.com/italy-fines-cloudflare-e14-million-for-refusing-to-filter-pirate-sites-on-public-1-1-1-1-dns/) · [Cloudflare blog — "Standing up for the open Internet: why we appealed Italy's 'Piracy Shield' fine"](https://blog.cloudflare.com/standing-up-for-the-open-internet/) · [TechRadar — Cloudflare CEO threatens to pull servers from Italy](https://www.techradar.com/vpn/vpn-privacy-security/cloudflare-ceo-threatens-to-pull-servers-from-italy-after-agcoms-eur14m-fine). Fine is 1% of global revenue; Cloudflare appealed Mar 8, 2026. **(b) Paris Court of Appeal, March 27, 2026 (RG 24/09372)** — rejected appeals by Google, Cloudflare, and Cisco; held that third-party public DNS resolvers *can* be compelled to block domains under Article L.333-10 (dynamic sports-rightsholder blocking). [TorrentFreak — Google, Cloudflare, Cisco Lose Pirate Site DNS Blocking Appeal in France](https://torrentfreak.com/google-cloudflare-cisco-lose-pirate-site-dns-blocking-appeal-in-france/) · [TorrentFreak — French Court Orders Google DNS to Block Pirate Sites (Jan 2026)](https://torrentfreak.com/french-court-orders-google-dns-to-block-pirate-sites-dismisses-cloudflare-first-defense/) · [heise online summary](https://www.heise.de/en/news/Google-DNS-Blocks-Paris-Court-Strengthens-Rights-Holders-Against-Pirates-11138592.html). Cisco pulled OpenDNS out of France pending appeal. The censorship-course DNS breakout has the current-events set: [censorship-course/docs/breakouts/dns.md](https://noise-lab.github.io/censorship-course/breakouts/dns). Teaching point: encryption solved confidentiality on the wire but made the trust/availability problem worse *and* concentrated the takedown target. |
| **The Core DoH Flaw: One Server Sees Both** | The privacy failure is the *coupling* of identity and query at a single point. Decouple them and you get privacy without trusting any single resolver fully. |
| **How Oblivious DNS Works** | Encrypted with the *target's* key, not the proxy's — that's what blinds the proxy. Reference: [RFC 9230 — Oblivious DNS over HTTPS (June 2022)](https://datatracker.ietf.org/doc/html/rfc9230). Original academic paper: [Edmundson, Schmitt, Feamster, Mankin — "Oblivious DNS: Practical Privacy for DNS Queries," PoPETS 2019](https://petsymposium.org/popets/2019/popets-2019-0028.php). IETF presentation: [DPRIVE slides, IETF 102, July 2018](https://datatracker.ietf.org/meeting/102/materials/slides-102-dprive-oblivious-dns-01). |
| **From Rejected Idea to Deployed Standard** | Cloudflare's deployment writeup: [Cloudflare 1.1.1.1 docs — Oblivious DoH](https://developers.cloudflare.com/1.1.1.1/encryption/oblivious-dns-over-https/). Apple iCloud Private Relay uses ODoH-style splitting between an Apple ingress proxy and a third-party egress (Cloudflare, Akamai, or Fastly): [About iCloud Private Relay — Apple Support](https://support.apple.com/en-us/102602). The research-process lesson: if a good idea makes people angry, keep running. The latency objection was empirically wrong (see the DoH CDF slide). |
| **Distributing Queries Across Resolvers** | The decentralization endgame: no single resolver, oblivious or not, should see your full query stream. Leaves an open research question — good material for the breakout / debate. |
| **What to Take Away** | Map each bullet to a likely midterm question: trace a lookup, DNSSEC hierarchy, what DNSSEC does/doesn't protect, the DoH before/after trust model, ODoH split. End on the recurring theme: every fix relocates trust rather than removing it. |
