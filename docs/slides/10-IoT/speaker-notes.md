|  | **Why the Smart Home Is Hard** | Frame the lecture: this is where *security* (devices can be discovered and controlled) and *privacy* (devices leak what you do at home) collide. Recurring research question: *"what are these devices doing, and who are they talking to?"* Companion breakout: [Device Privacy (IoT) breakouts](../../breakouts/iot.md). |  | **Two Questions That Drive the Lecture** | Roadmap: first half is web-based attacks that cross the boundary from browser to LAN; second half is measurement studies (IoT Inspector + the smart TV crawler). Tie back to earlier lectures — [same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy), third-party tracking, DNS — all reappear here. |
|  | **Studying IoT Is Genuinely Hard** | Methodological setup. Anecdotes don't generalize; [Shodan](https://www.shodan.io/) only sees what's *exposed*; the interesting traffic is behind NAT. Heterogeneity of protocols: Wi-Fi, [Z-Wave](https://en.wikipedia.org/wiki/Z-Wave), [Zigbee](https://csa-iot.org/all-solutions/zigbee/), [BLE](https://en.wikipedia.org/wiki/Bluetooth_Low_Energy). IoT Inspector + the TV crawler are answers to this observability problem. |
|  | **Four Ways to Study IoT, Compared** | • Recovered from the original pptx (slide 100); the build is gone, so walk the table a row at a time.<br><br>• **Scale:** web and mobile have crawlers and app stores; lab studies stop at the bench; Internet scanning ([Shodan](https://www.shodan.io/)-style) scales but only over exposed devices; crowdsourcing's scale is the open question.<br><br>• **Active probing:** every approach can poke a device; passive traffic from real homes is what only the lab and crowdsourcing see, and only crowdsourcing sees it at scale.<br><br>• **What to say:** the question mark in the crowdsourcing cell is the research bet of IoT Inspector, answered two slides on with 5,000 users and 50,000 devices. |
|  | **Many IoT Devices Run an Unauthenticated Web Server** | The key insight of **Acar, Huang, Li, Narayanan, Feamster, ["Web-based Attacks to Discover and Control Local IoT Devices,"](https://www.usenix.org/system/files/soups2018-acar_0.pdf)** SIGCOMM 2018 Workshop on IoT Security & Privacy. Circa 2015 the team bought the top devices on Amazon expecting hard reverse engineering — and found almost no encryption. The device's "API" is just an open web server, so the browser security model *becomes* the IoT security model. |
|  | **Attack 1: Discover Local Devices from a Web Page** | Three-step attack; step 3 is the clever part — the differing HTML5 [`MediaError`](https://developer.mozilla.org/en-US/docs/Web/API/MediaError) strings ("DEMUXER_ERROR..." vs "Format error") leak cross-origin existence, a **new side channel** the SOP is supposed to prevent. Chrome paid a bug bounty. Safari timed the fetches out; Edge gave no error strings; the attack didn't work there. WebRTC local-IP leakage anchor: [MDN on RTCPeerConnection](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection). |
|  | **Attack 1 in One Picture: Timing the LAN Scan** | • Recovered from the original pptx (slide 7); static, so narrate the two arrows.<br><br>• The page knows it is 192.168.6.6 from the WebRTC leak and sends a fetch to each address on the subnet, which the browser turns into a TCP SYN to port 81.<br><br>• The live smart plug at .88 answers at once (RST if the port is closed, SYN-ACK if open); the empty .89 never answers, so the fetch hangs until the browser gives up: the "?" is that wait.<br><br>• Fast failure means a host is there, slow failure means nothing is; no response body is ever read, so the SOP never gets a say.<br><br>• **What to say:** this is port scanning with the victim's own browser as the scanner; ask what a router could do about it (nothing, it is all local). |
|  | **Attack 2: DNS Rebinding to Control Devices** | Original 1996 paper: **[Dean, Felten, Wallach, "Java Security: From HotJava to Netscape and Beyond," IEEE S&P 1996](https://www.cs.princeton.edu/sip/pub/oakland96.html)** — birth of the DNS rebinding attack. Modern write-up: [Brannon Dorsey's 2018 disclosure](https://medium.com/@brannondorsey/attacking-private-networks-from-the-internet-with-dns-rebinding-ea7098a2d325) — demonstrated on Google Home / Chromecast (arbitrary YouTube playback, reboot, Wi-Fi scanning). Fix classes: [DNS pinning](https://en.wikipedia.org/wiki/DNS_rebinding#Protection), rejecting private IPs in public DNS responses, [Host header](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Host) allow-listing on the device, [Chrome PNA](https://developer.chrome.com/blog/private-network-access-preflight/). |
|  | **DNS Rebinding in Two Pictures** | • Recovered from the original pptx (slides 17 and 22, the first with the later HTTP overlay stripped); narrate left then right.<br><br>• Left: the browser asks attacker.com's authoritative server and gets 6.6.6.6 with TTL 1, so the record is discarded almost immediately; the page loads from the attacker's server and starts polling.<br><br>• Right: on the next lookup the same nameserver answers 192.168.6.88, so "attacker.com" now means the smart plug; GET /setup.xml goes straight to the device, comes back 200, and the page can read it because its origin never changed.<br><br>• **What to say:** the SOP keys on the hostname, the network keys on the IP, and the attacker controls the mapping between them; defenses are DNS pinning, refusing private addresses in public answers, Host-header checks, and Chrome's Private Network Access.<br><br>• Original: [Dean, Felten, Wallach, IEEE S&P 1996](https://www.cs.princeton.edu/sip/pub/oakland96.html). |
|  | **Why These Attacks Matter** | Connect to the [Mirai → Dyn Oct 2016 DDoS](https://en.wikipedia.org/wiki/Mirai_(malware)) from the DDoS lecture — IoT is attractive to attackers *because* it is unpatched and unisolated. Takeaway: the LAN must be treated as **zero-trust**. |
|  | **IoT Inspector: Crowdsourcing Home-Network Traffic** | Project home: **[iot-inspector.princeton.edu (Princeton)](https://inspector.cs.princeton.edu/)** — now also hosted at **[inspector.engineering.nyu.edu (NYU)](https://inspector.engineering.nyu.edu/)** under Danny Yuxing Huang. Paper: **[Huang, Apthorpe, Acar, Li, Feamster, "IoT Inspector: Crowdsourcing Labeled Network Traffic from Smart Home Devices at Large Scale," PoPETS 2020 / arXiv 1909.09848](https://arxiv.org/abs/1909.09848)**. Publicly released May 2019; 5,000+ users, 50,000+ devices worldwide. Coverage: [TechCrunch, Apr 2019](https://techcrunch.com/2019/04/13/spy-on-your-smart-home-with-this-open-source-research-tool/) · [CITP announcement](https://blog.citp.princeton.edu/2018/04/23/announcing-iot-inspector-a-tool-to-study-smart-home-iot-device-behavior/). Recent extensions: **[He et al., "Can Allowlists Capture the Variability of Home IoT Device Network Behavior?" EuroS&P 2024](https://homes.cs.washington.edu/~weijiah/papers/2024-eurosp-allowlists.pdf)** · [Kumar et al., "Connecting the Dots: Tracing Data Endpoints in IoT Devices," PoPETS 2024](https://petsymposium.org/popets/2024/popets-2024-0027.php). |
|  | **How It Sees the Traffic: ARP Spoofing** | Same primitive an attacker would use — turned into a benign measurement tool with user consent. Refresher: [ARP has no authentication](https://en.wikipedia.org/wiki/ARP_spoofing). Consent + on-device design is what makes this ethical. |
|  | **ARP Spoofing, Pictured** | • Recovered from the original pptx (slide 105); the two callouts appeared on successive clicks, so say them in order.<br><br>• To the router: the lightbulb's IP is at my MAC; to the lightbulb: the router's IP is at my MAC; both now forward through the laptop, which records and relays, and the same is done for the camera and every other device the user selects.<br><br>• [ARP (RFC 826)](https://datatracker.ietf.org/doc/html/rfc826) has no authentication, so neither side can tell; this is the same primitive an attacker would use, run with the owner's consent on the owner's network.<br><br>• **What to say:** ask what it would take to make ARP safe (static tables, 802.1X, DHCP snooping on a managed switch) and why none of that exists on a home router. |
|  | **Inferring the Inbound Rate from ACK Numbers** | • Recovered from the original pptx (slide 107); the braces on the right built up one at a time.<br><br>• Some routers accept the spoofed ARP in one direction only, so IoT Inspector sees what the camera sends (green) but not what it receives (orange).<br><br>• Every outbound TCP segment carries the camera's cumulative ACK number: Ack 1 to Ack 51 means 50 inbound bytes arrived in between, Ack 51 to Ack 72 means 20 more; difference the ACKs over time and you have the inbound rate without seeing a single inbound packet.<br><br>• Misses UDP and is coarse, but enough for the dashboard's bandwidth graph.<br><br>• Refresher on sequence and acknowledgment numbers: [TCP, RFC 9293](https://datatracker.ietf.org/doc/html/rfc9293). |
|  | **What Devices Talk To** | The "aha" screenshot: [Ira Flatow's Roku session on Science Friday (Oct 2019)](https://www.sciencefriday.com/segments/smart-home-privacy/) — a single streaming session fans out to dozens of tracking domains (doubleclick, scorecardresearch, [Conviva](https://www.conviva.com/), etc.). Point out the TLS-hygiene selectors ("no encryption / insecure / weak") at the top of the dashboard. |
|  | **Findings from 50,000 Devices** | Distributions, not anecdotes, move regulators. "**14.9% of smart TVs contact ad/tracking services**" is the kind of claim you can put in front of a regulator. Segue: to know *what* leaks (not just *to whom*), you need to decrypt — motivates the TV lab study next. |
|  | **Ineffective Encryption, by Vendor** | • Recovered from the original pptx (slide 113); no build.<br><br>• IoT Inspector records the TLS ClientHello, so this is what each device offers before any negotiation: TLS 1.0 from 31 Google, 67 Amazon, and 41 Samsung devices; SSL 3.0 from five Amazon devices, deprecated in 2015 after POODLE; RC4, broken since 2002, from 397 of 614 Amazon devices and 80 of 148 Samsung devices.<br><br>• **What to say:** offered, not necessarily negotiated; a server that refuses RC4 protects the device anyway, but a device that offers it is one downgrade away from using it, and brand is no proxy for crypto hygiene.<br><br>• Segue to the lab study: to know what is inside those connections you have to decrypt them. |
|  | **Cord-Cutting Created a New Tracking Surface** | The TV-crawler study: **[Mohajeri Moghaddam, Acar, Yu, Li, Vallina-Rodriguez, Feamster, "Watching You Watch: The Tracking Ecosystem of Over-the-Top TV Streaming Devices," ACM CCS 2019](https://dl.acm.org/doi/10.1145/3319535.3354198)** — first large-scale measurement of thousands of channels on Roku and Fire TV. Contrast with in-the-wild IoT Inspector: here we go into the lab to *decrypt* and read content, trading scale for depth. |
|  | **Building a Smart-TV Crawler** | Engineering is the contribution: there's no [Selenium](https://www.selenium.dev/) for a TV. Audio-detection as a playback oracle (96%, ~144/150) is the clever bit. Decryption is the hard part — [certificate pinning](https://owasp.org/www-community/controls/Certificate_and_Public_Key_Pinning) means TLS is often unreadable; they rooted Fire TV and used **[Frida](https://frida.re/)** to defeat per-channel pinning, and still only decrypted ≥1 connection from ~5% of channels on the harder platform. Be honest about that limitation. |
|  | **The Crawler Rig** | • Recovered from the original pptx (slide 124); the arrows appeared one build step at a time, so trace them.<br><br>• Remote-control commands go to the stick over the platform's developer interface; the stick's HDMI output goes into a capture card, which returns video and audio over USB; the stick's network traffic is routed through the laptop so every packet is captured.<br><br>• A web crawler gets the DOM, screenshots, and a network log for free; for a device with no automation API all three were rebuilt from hardware.<br><br>• **What to say:** the capture card is the key piece; without it the crawler is blind and deaf and cannot tell whether a channel ever played anything. Paper: [Mohajeri Moghaddam et al., CCS 2019](https://dl.acm.org/doi/10.1145/3319535.3354198). |
|  | **Audio as the Playback Oracle** | • Recovered from the original pptx (slide 129); the lower boxes appeared on successive clicks.<br><br>• No API says "a video is playing," so the crawler listens for five seconds of audio on the HDMI capture.<br><br>• On Roku, audio was detected in 62% of visits and a manual sample found 96% of those were real playback; of the 38% with no audio, about three quarters were channels the brute-force navigation got stuck in and the rest had no video to play.<br><br>• **What to say:** the honest coverage number is what makes the tracker percentages on the later slides believable; ask what a channel could do to fool this oracle (silent video, a menu with background music) and why no channel bothers. |
|  | **Almost Every Channel Talks to a Known Tracker** | Two things to draw out: (1) the same tracking oligopoly that runs the web has colonized your TV — [DoubleClick](https://en.wikipedia.org/wiki/DoubleClick), [google-analytics](https://analytics.google.com/), [ScorecardResearch](https://scorecardresearch.com/), [amazon-adsystem](https://advertising.amazon.com/); (2) they also found *previously unknown* trackers (received Ad ID / device serial, contacted by multiple channels, on **no filter list**) — meaning blocklists structurally miss new entrants. |
|  | **Children's Privacy: COPPA Enters the Picture** | Anchor case: **[FTC + NY AG v. Google & YouTube, Sept 4, 2019 — $170M COPPA settlement](https://www.ftc.gov/news-events/news/press-releases/2019/09/google-youtube-will-pay-record-170-million-alleged-violations-childrens-privacy-law)** for collecting persistent identifiers from viewers of child-directed channels without parental consent. The TV crawler found the same pattern on streaming platforms. Follow-on IoT precedent: **[FTC settlements with Amazon Ring & Alexa, May 31, 2023 — $31M total](https://www.ftc.gov/news-events/news/press-releases/2023/05/ftc-doj-charge-amazon-violating-childrens-privacy-law-keeping-kids-alexa-voice-recordings-forever)** ([Ring $5.8M](https://www.ftc.gov/legal-library/browse/cases-proceedings/2023113-ring-llc) for employee snooping on customer bedroom cameras; [Alexa $25M](https://www.ftc.gov/legal-library/browse/cases-proceedings/192-3128-amazoncom-alexa-us-v) for indefinite retention of children's voice recordings; Amazon barred from training models on data users deleted). Bridge to privacy-law lectures: a technical measurement finding maps directly onto a legal regime ([COPPA](https://www.ftc.gov/legal-library/browse/rules/childrens-online-privacy-protection-rule-coppa)) and a concrete penalty. Companion breakout: [IoT breakouts](../../breakouts/iot.md). |
|  | **Child-Directed Channels That Leaked Persistent IDs** | • Recovered from the original pptx (slide 138); no build.<br><br>• Of the crawled channels, 470 on Roku and 220 on Fire TV sat in the platforms' own kids categories; 34 and 23 of those sent a persistent identifier (Ad ID, Android ID, serial number) to a third party during one video play, with no parental consent asked.<br><br>• The original slides say the team was "working with the FTC for further investigations"; the [YouTube $170M settlement](https://www.ftc.gov/news-events/news/press-releases/2019/09/google-youtube-will-pay-record-170-million-alleged-violations-childrens-privacy-law) on the previous slide is the price of the same conduct on the web.<br><br>• **What to say:** small absolute numbers, but COPPA is strict about consent, and the platform's own category label is what makes a channel child-directed. |
|  | **The Opt-Outs Don't Really Work** | Policy punchline of the deck. Roku's "Limit Ad Tracking" and Amazon's "No interest-based ads" are theater — channels still shared persistent IDs; [Pi-hole](https://pi-hole.net/) DNS blocking crashes some channels; previously unknown trackers evade every standard filter list. Debate question: should the burden be on the consumer (notice-and-choice) or the platform/regulator (defaults + enforcement)? See [IoT Debate](../../debates/iot.md). |
|  | **What the Toggles Actually Changed** | • Recovered from the original pptx (slide 145); no build.<br><br>• The crawl was repeated with Roku's "Limit Ad Tracking" and Amazon's "No interest-based ads" on: Roku's Ad-ID sharing went from 30% to 0% but serial-number sharing barely moved (14% to 13%); on Fire TV, Ad-ID sharing halved (35% to 16%) while the Android ID still left from 65% of channels and serial number and MAC address were untouched.<br><br>• **What to say:** the toggle governs the one identifier the platform mints and can reset; it cannot reach the hardware identifiers that channels and their SDKs read for themselves, and those cannot be reset.<br><br>• The technical core of the "opt-outs are theater" argument on the previous slide and the hook for the debate. |
|  | **A 2026 Vignette: States Go After Your TV** | The freshest hook and the strongest research → policy arc in the course. **[Texas AG, "Attorney General Ken Paxton Sues Five Major Television Manufacturers…" Dec 15, 2025](https://www.texasattorneygeneral.gov/news/releases/attorney-general-ken-paxton-sues-five-major-television-manufacturers-alleged-privacy-violations)** naming Samsung, Sony, LG, Hisense, TCL over ACR. First-ever **TRO against a TV maker (Hisense)** two days later. **[Samsung settlement — Feb 26, 2026](https://www.texasattorneygeneral.gov/news/releases/attorney-general-paxton-secures-major-agreement-samsung-ensure-texans-are-protected-smart-tvs)** — express consent, no fine ([Malwarebytes summary](https://www.malwarebytes.com/blog/news/2026/03/samsung-tvs-stop-spying-on-viewers-in-texas-heres-how-to-disable-acr-anywhere) · [The Record](https://therecord.media/samsung-updates-acr-privacy-practices-texas)). **LG settlement — May 11, 2026** with an added no-transfer-to-CCP clause ([State of Surveillance roundup](https://stateofsurveillance.org/news/smart-tv-acr-lawsuits-samsung-settlement-roundup-2026/)). Sony, Hisense, TCL still fighting as of mid-2026. **Kentucky** passed the first ACR-specific consent statute ([IAPP overview](https://iapp.org/news/a/automated-content-recognition-technology-takes-privacy-enforcement-spotlight)). Precedent: [Vizio $2.2M FTC/NJ ACR settlement, Feb 2017](https://www.ftc.gov/news-events/news/press-releases/2017/02/vizio-pay-22-million-ftc-state-new-jersey-settle-charges-it-collected-viewing-histories-11-million). Ask: why did it take state AGs, not the FTC? Connect to the state-vs-federal privacy patchwork. |
|  | **Putting It Together** | Land the three threads: (1) LAN must be treated as untrusted; (2) tracking economy followed us web → mobile → home → TV; (3) measurement at scale is what makes anything policy-relevant. **EU regulatory horizon:** [Cyber Resilience Act](https://digital-strategy.ec.europa.eu/en/policies/cyber-resilience-act) (in force Dec 10, 2024; reporting duties from **Sept 11, 2026**; full obligations Dec 11, 2027; connected toys are Class I "important products with digital elements"); [EU AI Act](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai) as amended by the June 2026 "Digital Omnibus on AI" (high-risk embedded-in-products provisions now Aug 2, 2027 / stand-alone Dec 2, 2027). U.S. side: the [**U.S. Cyber Trust Mark**](https://www.fcc.gov/CyberTrustMark) is a *voluntary* label, not a mandate. Debate: [IoT Debate](../../debates/iot.md). |
