| 7 | **Passwords Are Losing; Passkeys Are Winning** | The slide now leads with the concept: a password is a shared secret that has to travel; a passkey is a per-site key pair whose private half never leaves the device, and signing in means signing the site's challenge plus the site's name. Say that first, in those words. The step-by-step flows are on slide 8; the three current-event cases below are the evidence that the shift is happening and where its edges are. Adoption anchors verified this session. **FIDO Alliance State of Passkeys 2026 (World Passkey Day, May 7, 2026):** [FIDO Alliance announcement](https://fidoalliance.org/fido-alliance-reports-accelerating-global-passkey-adoption-on-world-passkey-day-2026/) · [BusinessWire release](https://www.businesswire.com/news/home/20260506926067/en/FIDO-Alliance-Reports-Accelerating-Global-Passkey-Adoption-on-World-Passkey-Day-2026). 5B passkeys in use; ~48% of top-100 sites; 75% of consumers enabled ≥1 passkey; 68% of orgs deploying/piloting. **NIST SP 800-63-4 (finalized July 31, 2025):** [official final publication](https://csrc.nist.gov/pubs/sp/800/63/4/final). AAL2 verifiers **must offer** a phishing-resistant option; AAL3 **requires** device-bound non-exportable private keys. Yubico explainer of the new phishing-resistant definition: [Yubico blog](https://www.yubico.com/blog/nist-sp-800-63-4-what-the-new-phishing-resistant-definition-means-for-federal-agencies/).<br><br>Three fresh stories, in the order to tell them: the adoption milestone (passkeys became the default), the research that found the edges (Pass-the-Passkey), and the attackers' answer (use the word "passkey" as bait).<br><br><b>Case: passkeys became the default sign-in for Microsoft Entra ID (Sept 1, 2026)</b><br><br>**Read first:** [Microsoft Security Blog — "Microsoft Entra ID security updates: Passkeys are the default authentication method in Entra ID" (July 13, 2026)](https://www.microsoft.com/en-us/security/blog/2026/07/13/microsoft-entra-id-security-updates-passkeys-are-the-default-authentication-method-in-entra-id/) — the announcement by Microsoft's identity engineering lead, with the full timeline.<br><br>**What happened:**<br><br>• Microsoft announced on July 13, 2026 that passkeys become the default authentication experience in Entra ID from Sept 1, 2026, with SMS/voice users auto-enrolled into a passkey registration campaign at their next MFA sign-in.<br>• Microsoft-provided SMS and voice MFA retires Feb 1, 2027 for ordinary users (July 1, 2027 for Global Administrators and external users), after which the passkey prompt is blocking and there is no opt-out.<br>• Entra supports both synced passkeys (iCloud Keychain, Google Password Manager) and device-bound ones (Authenticator, Windows Hello, FIDO2 keys).<br>• Status as of Oct 7, 2026: rollout under way; SpecterOps says the full chain is now broken and has not seen it used outside test environments.<br>• Palo Alto Networks Unit 42 (Arie Olshtein, Aug 3, 2026) showed that malware on a Windows machine, without admin rights, could sign in with Chrome's Google-synced passkeys ("Pass-ta-key"), and in the "Golden" variant could recover the private keys outright because the 32-byte Security Domain Secret that encrypts them was exposed in Chrome's device logs and process memory; the server just accepted a *replay*.<br>• That is a failure of 'check current authority at time of use' — the 1975 principle on slide 24 — not a failure of public-key crypto.<br>• The Google one is worse in one specific way: synced passkeys are encrypted with one master secret per account that Chrome had been logging to disk, and there's no way to rotate it.<br>• So, cold-call: what's the trade-off between a synced passkey and a device-bound one? | 8 | **How a Passkey Actually Works** | Mechanics slide; no current event needed, the previous row carries the 2026 cases. Walk the two flows on the board.<br><br>**Read first:** [webauthn.guide — Guide to Web Authentication](https://webauthn.guide/) — the clearest end-to-end walkthrough of both flows, with the actual browser calls.<br><br>**What happens, registration:**<br>• The site (relying party) sends a random challenge plus its relying-party ID, which must be the site's own domain or a parent of it.<br>• The browser calls the authenticator; the user unlocks it with a biometric or PIN.<br>• The authenticator generates a brand-new key pair scoped to that relying-party ID, keeps the private key, and returns the public key plus a credential ID.<br>• The site checks that the returned challenge and origin match what it sent and stores the public key and credential ID with the account.<br><br>**What happens, sign-in:**<br>• The site sends a fresh random challenge and the credential IDs it will accept.<br>• The browser passes the challenge and the current origin to the authenticator; the user unlocks it again.<br>• The authenticator signs the authenticator data (relying-party ID hash, a use counter, flags) together with a hash of the client data (challenge, origin, type) using the private key.<br>• The site verifies the signature with the stored public key and confirms the challenge is the one it issued and the origin is its own.<br><br>**What to say:**<br>• "Three things cross the wire at sign-in: a random number the site made up, the name of the site, and a signature over both. Nothing reusable, nothing secret."<br>• "The private key signs the origin. So if you are on a lookalike domain, two things happen: the browser will not even offer the credential, because it was registered for a different domain, and even if it did, the signature would name the wrong site and the real site would reject it. The user never has to notice the URL. That is what phishing-resistant means."<br>• "If the site is breached, the attacker gets a pile of public keys. Useless."<br>• "Every challenge is used once, so a recorded sign-in cannot be replayed. Hold that thought: the Pass-the-Passkey research is about what happens when the verifier gets that part wrong."<br>• Cold-call: where does a synced passkey live, and who can read it? (On every device under the same cloud account, encrypted so the provider cannot; recovery is the benefit, a compromised cloud account is the risk.)<br><br>**Course tie-in:**<br>• The three modes: the private key is something you have; the biometric or PIN is something you are or know; one gesture does both, which is why NIST counts it as phishing-resistant MFA.<br>• Public-key crypto from the first hour, used for integrity not confidentiality: sign with the private key, verify with the public key. Same math as a certificate, but each user is their own key holder.<br>• NIST 800-63-4: AAL2 must offer a phishing-resistant option (synced passkeys qualify); AAL3 requires device-bound, non-exportable keys.<br>• The previous slide's attacks all assume code already inside the device that holds the private key; none of the three guarantees on this slide covers that.<br><br>**Also:**<br>• [passkeys.dev — What are passkeys?](https://passkeys.dev/docs/intro/what-are-passkeys/) — the developer-facing definition: unique per service, server holds only public keys, browsers enforce the site binding.<br>• [FIDO Alliance — Passkeys](https://fidoalliance.org/passkeys/) — synced vs device-bound, and cross-device sign-in: a phone approves a laptop login after a QR scan, with Bluetooth proving proximity (the CTAP hybrid transport). |
