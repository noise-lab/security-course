| Slide | Context + Links |
|---|---|
| **What Access Control Is For** | Framing from the [Tanenbaum & Bos, *Modern Operating Systems* (4th ed., 2015)](https://www.pearson.com/en-us/subject-catalog/p/modern-operating-systems/P200000003554/) — protection goals in Ch. 9. The four goals (user↔user, app↔app, system↔network, allow sharing) form the isolation-vs-sharing tension that structures the whole lecture. Cold-call target: "where did you hit a 'permission denied' this week?" |
| **The Threat Model Has Shifted** | The pivot from 1970s multi-user mainframes (trusted apps) → PC OS inheriting the model (apps get user's full privileges) → smartphones as ground-up "untrusted app" OS. Modern browser-as-OS observation: [Ian Hickson (Google, 2010) — "The browser is the new OS"](https://www.w3.org/wiki/HTML/) and Chrome's [Sandbox design doc](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md). Cloud/SaaS tenants as "the new multi-user mainframe": [Google Cloud multi-tenancy overview](https://cloud.google.com/architecture/framework/system-design/multi-tenancy). |
| **Who Are You Defending Against?** | Adversary taxonomy from [Tanenbaum & Bos, Ch. 9.1](https://www.pearson.com/en-us/subject-catalog/p/modern-operating-systems/P200000003554/). Passive vs active + security vs privacy is the [Saltzer–Schroeder (1975)](https://www.cs.virginia.edu/~evans/cs551/saltzer/) framing. UNC6395 = the Aug 2025 Salesloft-Drift threat actor (later slide). |
| **Identification, Authentication, Authorization** | The exam-critical distinction. Canonical treatment: [NIST SP 800-63-4 (final, July 31, 2025) — Digital Identity Guidelines](https://csrc.nist.gov/pubs/sp/800/63/4/final). See especially [SP 800-63B (Authentication)](https://pages.nist.gov/800-63-4/sp800-63b.html) for the identify/authenticate/authorize/accountability sequence. Physical analogy: badge (ID) → guard-check (authN) → door list (authZ) → reader log (accountability). |
| **The Three Modes of Authentication** | Know/have/are — flagged as midterm material in `agenda.md` Meeting 3. Reference: [NIST SP 800-63B §5 "Authenticator and Verifier Requirements"](https://pages.nist.gov/800-63-4/sp800-63b.html). Biometrics "can't revoke a fingerprint" — see [NAS 2010 report *Biometric Recognition: Challenges and Opportunities*](https://nap.nationalacademies.org/catalog/12720/biometric-recognition-challenges-and-opportunities). Legal wrinkle: US case law on compelled biometric unlock (5th Amendment) — [EFF backgrounder](https://www.eff.org/deeplinks/2019/01/victory-judge-rules-police-need-warrant-track-cell-phones). |
| **Passwords Are Losing; Passkeys Are Winning** | Vignette anchors verified this session. **FIDO Alliance State of Passkeys 2026 (World Passkey Day, May 7, 2026):** [FIDO Alliance announcement](https://fidoalliance.org/fido-alliance-reports-accelerating-global-passkey-adoption-on-world-passkey-day-2026/) · [BusinessWire release](https://www.businesswire.com/news/home/20260506926067/en/FIDO-Alliance-Reports-Accelerating-Global-Passkey-Adoption-on-World-Passkey-Day-2026). 5B passkeys in use; ~48% of top-100 sites; 75% of consumers enabled ≥1 passkey; 68% of orgs deploying/piloting. **NIST SP 800-63-4 (finalized July 31, 2025):** [official final publication](https://csrc.nist.gov/pubs/sp/800/63/4/final). AAL2 verifiers **must offer** a phishing-resistant option; AAL3 **requires** device-bound non-exportable private keys. Yubico explainer of the new phishing-resistant definition: [Yubico blog](https://www.yubico.com/blog/nist-sp-800-63-4-what-the-new-phishing-resistant-definition-means-for-federal-agencies/). |
| **A Common Framework: Subject, Verb, Object** | The (subject, verb, object) triple is from the [Lampson access matrix (1971)](https://dl.acm.org/doi/10.1145/775265.775268). Run the Facebook exercise as a 60-second breakout — subjects (you, friend, News Feed ranker, ad partner); verbs (read/post/tag/delete/share); objects (photo, wall, DM). |
| **ACLs vs. Capabilities** | Foundational: [Dennis & Van Horn (1966) *Programming Semantics for Multiprogrammed Computations*](https://dl.acm.org/doi/10.1145/365230.365252) — first capabilities paper. Modern treatment: [Miller, Yee, Shapiro, *Capability Myths Demolished* (2003)](http://www.erights.org/elib/capability/duals/myths.html). The seed for the OAuth half: tokens are capabilities → hard to revoke → 2025 breaches. |
| **Unix: A Simplified ACL Model** | Live demo: `ls -l`, `whoami`, `groups`, `ps` per agenda Meeting 3. Reference: [Unix file permissions (Wikipedia)](https://en.wikipedia.org/wiki/File-system_permissions#Traditional_Unix_permissions). Note `www-data`/`nobody` are conventional service users on Debian/Ubuntu (see `/etc/passwd` on any Linux box). |
| **The Principle of Least Privilege** | [Saltzer & Schroeder, "The Protection of Information in Computer Systems" (1975)](https://www.cs.virginia.edu/~evans/cs551/saltzer/) — principle #4. Ties OS half to OAuth half via scope. Historical hook: pre-2000 Apache running as root; see [OWASP Least Privilege](https://cheatsheetseries.owasp.org/cheatsheets/Access_Control_Cheat_Sheet.html). |
| **Phones: Per-App Sandboxes** | [Android Application Sandbox docs](https://source.android.com/docs/security/app-sandbox). Historical over-permission problem: [Felt et al., "Android Permissions Demystified" (CCS 2011)](https://dl.acm.org/doi/10.1145/2046707.2046779) — developers over-requested; users didn't read. Coarsening → permission groups → just-in-time. |
| **Make the Action the Permission** | iOS just-in-time contextual permissions: [Apple developer — Requesting Access to Protected Resources](https://developer.apple.com/documentation/uikit/protecting_the_user_s_privacy). The Uber "scan credit card" story is a classic Alex Russell / iOS UX example — combining *action* with *permission grant* in one tap. Coincides with Android 6.0's runtime-permission redesign (Oct 2015). |
| **Life Before OAuth: Just Share the Password** | Banking-aggregator antipattern — Mint, Plaid pre-open-banking. See [Plaid Exchange docs on OAuth migration](https://plaid.com/docs/link/oauth/) for the modern retrofit. The CFPB's [Personal Financial Data Rights rule (Oct 2024, Rule 1033)](https://www.consumerfinance.gov/rules-policy/final-rules/required-rulemaking-on-personal-financial-data-rights/) formalized OAuth-style token access for US financial data (Note: 2025 rule status has been contested — verify before lecturing). |
| **What OAuth 2.0 Actually Is** | Canonical spec: [RFC 6749 — OAuth 2.0 Authorization Framework (Oct 2012)](https://datatracker.ietf.org/doc/html/rfc6749). Modern update in progress: [OAuth 2.1 draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/) consolidates BCP 212 recommendations (mandatory PKCE, no implicit flow). |
| **The Four Roles** | Same source: [RFC 6749 §1.1](https://datatracker.ietf.org/doc/html/rfc6749#section-1.1). "Given a scenario (Slack + GitHub), identify OAuth roles" is flagged as a midterm question in `agenda.md`. Live demo per agenda: wire up the Slack GitHub app. |
| **The Flow, Six Steps** | Authorization Code Grant flow: [RFC 6749 §4.1](https://datatracker.ietf.org/doc/html/rfc6749#section-4.1). Refresh tokens: [§6](https://datatracker.ietf.org/doc/html/rfc6749#section-6). PKCE (public clients): [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636). Diagram image (`slide032_img011.png`) is the abstract flow — walk it with the printing-service-to-Google-Drive story. |
| **A Real OAuth Flow: Strava API** | [Strava OAuth 2.0 documentation](https://developers.strava.com/docs/authentication/). Ties to **Assignment 2**: build a third-party app against any OAuth API. Reference for [OAuth activity](../../activities/oauth.md). |
| **Tokens: Scope Is Least Privilege** | [GitHub personal access token docs — fine-grained tokens (GA March 2025)](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). JWT format: [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519). HS256 vs RS256: [Auth0 explainer](https://auth0.com/blog/json-web-token-signing-algorithms-overview/). |
| **When OAuth Goes Wrong** | Threat model: [RFC 6819 — OAuth 2.0 Threat Model and Security Considerations](https://datatracker.ietf.org/doc/html/rfc6819) and updated [OAuth 2.0 Security Best Current Practice (BCP 240 draft)](https://datatracker.ietf.org/doc/draft-ietf-oauth-security-topics/). `state` parameter: [RFC 6749 §10.12 (CSRF)](https://datatracker.ietf.org/doc/html/rfc6749#section-10.12). Redirect-URI exact match: [BCP 240 §4.1](https://datatracker.ietf.org/doc/draft-ietf-oauth-security-topics/). |
| **2025–26: Attackers Stopped Stealing Passwords** | **All figures verified this session.** **Salesloft–Drift (Aug 9–17, 2025):** primary sources — [Google Cloud Threat Intelligence — "Widespread Data Theft Targets Salesforce Instances via Salesloft Drift"](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift) · [The Hacker News](https://thehackernews.com/2025/09/salesloft-takes-drift-offline-after.html) · [Mitiga: ShinyHunters and UNC6395](https://www.mitiga.io/blog/shinyhunters-and-unc6395-inside-the-salesforce-and-salesloft-breaches) · [AppOmni breach recap](https://appomni.com/blog/drift-breach-salesforce-unc6395-saas-prevention/). Cloudflare disclosed **104 stolen Salesforce Case API tokens**. **Vercel/Context.ai (April 2026):** primary source — [Vercel Knowledge Base — April 2026 security incident](https://vercel.com/kb/bulletin/vercel-april-2026-security-incident) · [The Hacker News](https://thehackernews.com/2026/04/vercel-breach-tied-to-context-ai-hack.html) · [SpecterOps: OAuth as identity attack path](https://specterops.io/blog/2026/04/21/the-vercel-breach-explains-why-identity-attack-path-management-cant-wait/) · [Trend Micro OAuth supply-chain analysis](https://www.trendmicro.com/en_us/research/26/d/vercel-breach-oauth-supply-chain.html). CEO Guillermo Rauch confirmed on X; $2M ransom via BreachForums. **AiTM PhaaS kits (2026):** [Microsoft Security Blog — Inside Tycoon2FA (Mar 4, 2026)](https://www.microsoft.com/en-us/security/blog/2026/03/04/inside-tycoon2fa-how-a-leading-aitm-phishing-kit-operated-at-scale/) · [Proofpoint — Tycoon 2FA phishing kit](https://www.proofpoint.com/us/blog/email-and-cloud-threats/tycoon-2fa-phishing-kit-mfa-bypass) · [Security Boulevard — Tycoon 2FA loses phishing-kit crown (April 2026)](https://securityboulevard.com/2026/04/tycoon-2fa-loses-phishing-kit-crown-amid-surge-in-attacks/). Microsoft blocked **13M+ Tycoon 2FA messages in October 2025 alone**. Ask: would a passkey have stopped Salesloft–Drift? **No** — the token was already issued; this is post-auth abuse. Would it have stopped Vercel? **Also no** — the OAuth grant was legitimate; the *user* was compromised via infostealer. |
