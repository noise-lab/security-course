| **The Question Behind Everything Today** | One-sentence thesis: *"data must stay data."* Every attack in this deck is a syntactic confusion of the two — an untrusted string that the browser or server later re-interprets as code, script, or a request. This is the same failure mode as buffer overflows in the systems lecture; here the interpreter is SQL, HTML, or the browser's cookie machinery instead of the CPU. |
| **A 2026 Vignette: When the Firewall Has the Bug** | **CVE-2025-25257** (Fortinet FortiWeb Fabric Connector, unauthenticated SQLi → RCE, CVSS 9.6). Primary sources verified 2026-07-16: [watchTowr Labs technical write-up (July 11, 2025)](https://labs.watchtowr.com/pre-auth-sql-injection-to-rce-fortinet-fortiweb-fabric-connector-cve-2025-25257/) — the crafted `Authorization` header, `get_fabric_user_by_token`, `INTO OUTFILE` writing a `.pth` file into `site-packages` for RCE via a Python CGI. [CISA KEV catalog addition, July 18, 2025](https://www.cisa.gov/news-events/alerts/2025/07/18/cisa-adds-one-known-exploited-vulnerability-catalog). [Shadowserver Foundation daily counts](https://www.shadowserver.org/) — 85 compromised appliances on July 14, 77 the next day, down to 35 by July 18 as patches rolled. [BleepingComputer follow-up](https://www.bleepingcomputer.com/news/security/new-fortinet-fortiweb-hacks-likely-linked-to-public-rce-exploits/) · [SecurityAffairs coverage](https://securityaffairs.com/180118/hacking/fortinet-fortiweb-flaw-cve-2025-25257-exploited-hours-after-poc-release.html). Teaching point: a *SQL-injection-blocking product* shipped a SQL-injection bug that concatenated an HTTP header into a MySQL query — the FortiWeb bug is the FortiWeb bug's own use case. |
| **A Page Load, One Request at a Time** | • Recovered figure (original pptx slide 9); static, so walk the arrows in order: `GET /`, the HTML, the inline `alert('Hi!')`, then the image request and the PNG bytes.<br>• **What to say:** a page is a program the browser assembles from several round trips, and each round trip is a chance for another origin to join in.<br>• **Course tie-in:** sets the drawing vocabulary (green request, blue response, server icons) that every later SOP, XSS, and CSRF figure reuses.<br>• Reference: [MDN — How the web works](https://developer.mozilla.org/en-US/docs/Learn_web_development/Getting_started/Web_standards/How_the_web_works). |
| **Browser Security: The Goal** | Same-Origin Policy is the browser's foundational isolation rule. Overview reference: [MDN — Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy). The historical framing ("grafted on afterward") comes from the fact that Netscape 2 (1995) shipped JavaScript before SOP existed; SOP was retrofitted as a security patch. |
| **What Is an "Origin"?** | The `scheme + host + port` triple is the exam-style question every year. Canonical reference: [RFC 6454 — The Web Origin Concept](https://datatracker.ietf.org/doc/html/rfc6454). The subdomain row (`login.bank.com` ≠ `bank.com`) is where students lose points. |
| **The Rule, and the Key Question** | The "loading vs. reading" distinction is the *actual* SOP rule: cross-origin *sends* are legal; cross-origin *reads* are blocked. That's why CSRF works (write) but not full data theft (read). |
| **SOP in One Picture: A Cross-Origin Read, Blocked** | • Recovered figure (pptx slide 12): evil facebook.com page, its script asks gmail.com for `msgs.json`, gmail answers, the red X is on the *read*.<br>• **What to say:** the request is really sent, with the Gmail cookie, and gmail.com really answers; SOP acts inside the browser, between the response and the script.<br>• **Course tie-in:** the picture both CSRF (the send is enough) and XSS (move the script inside the origin and the read is allowed) are built on; come back to it twice.<br>• Reference: [MDN — Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy). |
| **Two Subtleties That Trip People Up** | **Scripts inherit the *embedding* origin's privileges** — this is why a compromised CDN script owns the page. The clean 2024 case (flagged in coverage-notes as an alternative vignette): [Polyfill.io supply-chain attack, Sansec forensics report (June 25, 2024)](https://sansec.io/research/polyfill-supply-chain-attack) — a Chinese CDN acquired the polyfill.io domain and served malware to ~100k websites through a legitimate third-party script tag. [Censys deep-dive (July 2, 2024)](https://censys.com/blog/july-2-polyfill-io-supply-chain-attack-digging-into-the-web-of-compromised-domains/). Andrew Betts (the polyfill's original author) had warned in Feb 2024: *"If your website uses http://polyfill.io, remove it IMMEDIATELY."* The mitigating defense is [Subresource Integrity (SRI)](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity) — a hash in the `<script>` tag that pins what the browser is willing to execute. Ties to the privacy/supply-chain lecture. |
| **Subtlety 1, Drawn: A Script Loaded From Another Origin** | • Recovered figure (pptx slide 16): facebook.com page with `<script src="https://gmail.com/chat.js">`; the browser fetches and runs it, then the script's `$.get` to gmail.com is blocked (the original's next slide showed the red X; narrate it).<br>• **Ask:** "what origin is chat.js running under?" Most say gmail.com; the answer is facebook.com, the embedding page.<br>• **Course tie-in:** this is the CDN story and the Polyfill.io supply-chain case from the previous row; [Subresource Integrity](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity) is the matching defense. |
| **Subtlety 2, Drawn: An iframe Keeps Its Own Origin** | • Recovered figure (pptx slide 19): facebook.com page embeds `<iframe src="https://gmail.com/chat">`; the script inside the frame reads gmail.com's `chat.json` successfully.<br>• **What to say:** same servers, same request as the script slide, opposite outcome; the only difference is the tag. A script tag merges into the embedding origin, an iframe keeps its own document and origin.<br>• **Course tie-in:** why embedded payment frames and login widgets are defensible; sets up XSS with "what if the attacker could get a script *into* the gmail.com frame?"<br>• Reference: [MDN — `<iframe>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe). |
| **Confusing Data and Code** | The one-slide thesis. Injection is a metavariable — the SQL/HTML/shell target is a syntactic detail, not the point. |
| **SQL: A Language to Question Databases** | Set up: user input lands *inside* the quotes of a query string that the DB will later re-parse. The moment concatenation happens, the attacker co-authors the query. |
| **SQL Injection** | The canonical `'; DELETE FROM ... WHERE '1'='1` walkthrough. Companion payload to have ready if a student asks: `' OR '1'='1'-- ` for authentication bypass. Explain each metacharacter (quote closes, `;` starts a new statement, `--` comments out the rest so no syntax error). |
| **Little Bobby Tables** | [xkcd 327 — "Exploits of a Mom"](https://xkcd.com/327/). Robert'); DROP TABLE Students;-- is the enduring mascot of the field. |
| **SQL Injection Defense: Make Data Stay Data** | **Prepared statements** are the *actual* answer — the query shape is sent to the DB first, and bound parameters can never become new statements. Reference: [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html). Callback to FortiWeb: the vendor concatenated an `Authorization` header into a MySQL query — a 2025 bug that a 2005 prepared statement would have prevented. |
| **XSS: HTML Injection Becomes Script Injection** | The three-stage escalation (`Bob` → `<u>Bob</u>` → `<script>`) is the pedagogical move: the moment the browser treats the input as *markup* instead of *text*, you have lost. |
| **Reflected XSS, Drawn: The Lure and the Echo** | • Recovered figure (pptx slide 30): the attacker's "Click me" link, the request to vuln.com with a script in `?user=`, the PHP echo, and the alert in the victim's browser.<br>• **What to say:** trace the attacker's bytes from the email into the URL, through the server's string concatenation, and back into the victim's browser; the server never ran anything, it failed to escape.<br>• **Ask:** who is the victim, the user or vuln.com? Both, which is why the next slides matter.<br>• Reference: [PortSwigger — Reflected XSS](https://portswigger.net/web-security/cross-site-scripting/reflected). |
| **Why XSS Is So Dangerous: It Defeats SOP** | Punchline of the whole arc: SOP is still being enforced perfectly — the attacker just made their code part of the trusted origin. Reference: [OWASP XSS Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html). Historical anchor: the [Samy worm on MySpace (2005)](https://en.wikipedia.org/wiki/Samy_(computer_worm)) — the first mass stored-XSS worm; added ~1M "friends" to Samy Kamkar's profile in 20 hours. |
| **The Attack, Step 1: Injecting the Script Into gmail.com** | • Recovered figure (pptx slide 32): the evil facebook.com response carries an iframe whose `src` is a gmail.com URL with a script in the `user` parameter; the browser requests it with the Gmail cookie; gmail.com echoes it back.<br>• **What to say:** the browser and SOP behave correctly throughout; the bug is gmail.com's missing output escaping. The devil icons mark where the attacker's bytes are at each step.<br>• **Course tie-in:** the "data became code" thesis, one layer up from SQL injection. |
| **The Attack, Step 2: Reading Your Mail From Inside the Origin** | • Recovered figure (pptx slide 33, final animation state with the first half faded): the injected script's `$.get` to `msgs.json` is now same-origin and the read succeeds.<br>• **What to say:** compare with the SOP picture earlier, same request and same server, opposite outcome, because the script's origin changed. SOP is still enforced perfectly.<br>• **Ask:** what replaces `alert()` in a real attack? A fetch to evil.com with the JSON in the body, which SOP also allows because sending is legal and the attacker never needs the reply.<br>• Historical anchor stays the [Samy worm (2005)](https://en.wikipedia.org/wiki/Samy_(computer_worm)) from the previous row. |
| **Reflected vs. Stored XSS** | 2026 refresh (verified 2026-07-16): [CVE-2026-0256 — PAN-OS stored XSS in the web interface (May 13, 2026)](https://security.paloaltonetworks.com/CVE-2026-0256) · [CVE-2026-0266 — a second PAN-OS stored-XSS variant (June 10, 2026)](https://security.paloaltonetworks.com/CVE-2026-0266) — both are stored XSS in a *firewall's* admin UI. WordPress plugin XSS example: [CVE-2026-1923 — Social Rocket plugin stored XSS](https://www.sentinelone.com/vulnerability-database/cve-2026-1923/). Wordfence tracks the ongoing plugin-XSS cadence: [Wordfence Intelligence Weekly WordPress Vulnerability Report](https://www.wordfence.com/blog/2026/04/wordfence-intelligence-weekly-wordpress-vulnerability-report-march-30-2026-to-april-5-2026/). |
| **XSS Defenses** | Context-aware output escaping is the primary defense; framework auto-escape (React, Django) makes it the default. **CSP** is the seatbelt: [MDN — Content Security Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/CSP). The friction bit is real — CSP that forbids `'unsafe-inline'` breaks a lot of legacy sites, so adoption is uneven. |
| **CSRF: The Browser Sends Your Cookie Automatically** | Ambient authority is the root cause: the cookie is attached to *every* request to the target origin, including cross-origin embed loads. Reference: [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Note this is allowed by SOP — sending a cross-origin request is fine; it's reading the *response* that's blocked. CSRF doesn't need to read anything. |
| **CSRF, Drawn: One Click, One Forged Transfer** | • Recovered figure (pptx slide 40): the bank's thought bubble `fde874 = bob`, the attacker's link, the request with `Cookie: login=fde874` attached automatically, the `-$100.00` response.<br>• **What to say:** point at the Cookie line, that is ambient authority, the single fact CSRF rests on; the attacker never reads the response, the side effect is the attack.<br>• The request is a GET for simplicity; a real bank uses POST, forged with an auto-submitting form, which `SameSite=Lax` now blocks by default.<br>• Reference: [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). |
| **A Realistic CSRF: Polluting What a Service Knows About You** | [Xing, Meng, Doozan, Snoeren, Feamster, Lee — *"Take This Personally: Pollution Attacks on Personalized Services,"* USENIX Security 2013](https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/xing) (search this session's canonical listing on [usenix.org/conference/usenixsecurity13](https://www.usenix.org/conference/usenixsecurity13/technical-sessions)). Reframes CSRF from "hypothetical bank transfer" to "quietly manipulating the model a service builds of you" — bridges to the tracking / personalization lectures. |
| **CSRF Defenses** | **Tokens** (embedded, unpredictable, per-session) are the classical defense — the attacker can't read the token because SOP forbids the cross-origin read. **SameSite=Lax** has been the Chrome default since [August 2020 (Chromium rollout)](https://www.chromium.org/updates/same-site/) and quietly neutered most drive-by CSRF. Gotcha for the paranoid: Chrome's "Lax+POST" 2-minute window means a freshly-set cookie *can* still ride a cross-site POST — see [PortSwigger — Bypassing SameSite restrictions](https://portswigger.net/web-security/csrf/bypassing-samesite-restrictions). Defense in depth: `SameSite=Lax` **and** tokens. |
| **The Token Defense, Drawn** | • Recovered figure (pptx slide 43): the hidden `token=8d64` field, `Set-Cookie: token=8d64`, the legitimate transfer carrying both cookie and token, and the `-$25.00` response. This is the "double-submit cookie" variant.<br>• **What to say:** narrate the failing flow the picture omits: evil.com can make the browser send the cookie but cannot fill in the token, because that would require reading a bank.com page cross-origin, which SOP forbids.<br>• **Course tie-in:** the rule that failed to stop the send is the rule that protects the token; everything in the lecture rhymes.<br>• Reference: [OWASP — Double Submit Cookie pattern](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#alternative-using-a-double-submit-cookie-pattern). |
| **What to Remember** | The one bug, four faces. Close by returning to the opening sentence: data must stay data. Callback to FortiWeb — a 25-year-old bug class, actively exploited in 2025, inside a security product. Note for students: TLS/HTTPS (which protects the *channel*) is covered in the PKI lecture; today was about the *application* on top of it. |
